# 云端常驻与设备协作设计

**日期：** 2026-10-23

**状态：** 目标架构提案；Q1 已有独立的私聊实现，见 [QQ_CHANNEL.md](QQ_CHANNEL.md)。
完整云端/设备协作与观察系统未实现；产品依据见 [PRODUCT.md](PRODUCT.md)。

**范围：** 云端唯一身份、QQ 接入、设备执行、档案、授权、恢复和验收。

本文的实体名和状态是设计词汇，不是已经存在的 Rust 类型、API、数据库表或新 crate。
最终协议与存储设计应在具体实现前单独评审。不要一次性搭建所有抽象。

## 1. 部署角色与状态归属

```text
用户 QQ ── NapCat 观察接入 ── 来源过滤与归档 ──┐
                                               │
用户 ←→ Lain QQ ←→ NapCat 交流接入 ←→ 云端 Kernel
                                               │
                           身份 / 对话 / 记忆 / 经历
                           活动调度 / 授权 / 工作监督
                                               │
                              经认证的设备连接与事件
                                  ┌────────────┴────────────┐
                               本地 PC A                 本地 PC B
                            终端 + 后台执行端          终端 + 后台执行端
                            Worker / 档案采集          Worker / 档案采集
```

NapCat 是外部消息通道，设备端是执行和采集节点；二者都不能各自成为身份或记忆的权威。
云端对运行中的 PC 只能拥有基于执行证据的投影，不能凭连接状态制造 Worker 结果。
一个云端权威不要求所有推理串行，也不要求所有对话窗口共用一份无限增长的上下文。

现有 laind 是本地 loopback 服务，直接管理本机 Worker。未来云端部署不应简单地将
监听地址改为公网：远端认证、传输保护、设备身份、撤销、凭证与发送边界需先设计。
不在本次文档中承诺具体云厂商、端口、通信协议、后台安装方式或容器方案。

## 2. 数据同步的单位

| 数据 | 权威写入方 | 缓存/副本 | 冲突原则 |
| --- | --- | --- | --- |
| 人格正式版本 | 云端受控配置入口 | 本地只读版本 | 显式版本变更，不能最后写入覆盖一切 |
| 语义记忆和关系认识 | 云端记忆服务 | 有限本地缓存 | 来源、修订、纠正和失效记录 |
| 技能与模板 | 云端资源管理 | 指定版本本地文件 | 任务固定版本，新任务可选择新版本 |
| 本机执行结果 | 对应设备/Worker 证据 | 云端归档和投影 | 基于事件身份和顺序去重 |
| 设备能力与路径 | 对应设备 | 云端目录 | 显示更新时间，不假定一直可用 |
| 认证材料 | 对应受控凭证系统 | 原则上不普通同步 | 间接引用，独立轮换与撤销 |

本地上传采用稳定的来源标识和去重身份，云端提交后确认接收位置。
至少一次传输与幂等接收比“网络永远可靠”更实际；不得宣称端到端 exactly-once。
事件发生时间、接收时间、来源顺序应分别保留，不能只靠设备时钟排序。
云端数据库的复制/备份不等于多台设备各自运行有独立写权限的身份数据库。

现有本地独立 laind 数据库不能自动与云端合并。迁移、导入和接管旧本地实例需要
具体工具与冲突规则，不得用同步文件隐式覆盖历史。

## 3. QQ 双账号边界

观察接入和交流接入分别配置账号身份、凭证、允许来源与能力，不能使用一个
无限制的通用 NapCat action 工具交给模型。

### 3.1 观察接入

- 仅归档用户选定的群/私聊；过滤应尽量发生在长期保存与模型处理之前。
- 允许获取相关消息、必要附件和上下文的具体接口仍需验证。
- 不允许发送、撤回、点赞、好友/群管理等写操作自动混入“读取”权限。
- 群里用户自己的发言也不自动成为当前命令；保留说话人与场景。
- 中断期间能补采多少取决于实际 NapCat/QQ 能力，缺口必须可见。

### 3.2 交流接入

- 用户 QQ 身份与产品用户身份应显式绑定，不能凭昵称推断。
- 允许与绑定用户双向交流；其他人发来的消息不自动成为有权限的请求。
- 群内发送、联系第三方和报名等有独立授权。
- 发送前再次检查当前授权、目标账号、接收者和提醒时效。
- 用户账号观察到 Lain 私聊时，识别为同一交流的镜像，避免再次触发推理。

### 3.3 来源身份与去重

候选来源键包括平台、接入账号、群/私聊目标、平台消息 ID 和事件种类。
不假定平台消息 ID 在不同账号视角中必定相同。跨账号无法可靠匹配时，不凭近似文本
删除独立消息；优先规定 Lain 私聊由交流接入作为主要记录，观察接入排除该镜像。
具体关联能力必须通过真实样本验证。

来源记录是资料，不是系统指令；整理、记忆和执行层应持续保留这一区别。

## 4. 档案与派生数据

建议区分：SourceRecord（来源记录）、SourceAsset（附件）、DerivedSummary（整理结果）、
Experience（实际经历）、Memory（选择性认识）、AttentionItem（尚在关注的事情）。
它们可使用同一存储技术，但有不同来源、生命周期与读取策略。

来源记录至少需要：稳定身份、来源/账号/会话、发送者、发生和接收时间、
回复/转发关系、内容或附件引用、采集位置、完整性及编辑/撤回状态（如果能观察到）。
模型未读过的档案不能自动标记为经历；看过摘要也不能声称阅读全文。

派生结果记录输入来源或范围、处理时间、版本和局限。原始消息更正或删除后，
能够找到受影响的摘要与认识，标记过时、重算或失效，而非留下独立流传的“事实”。

存储策略须覆盖：原文、附件、索引、摘要、人物事实、导出、备份和设备缓存。
停用采集只停止未来采集；删除存量是另一个明确操作。禁止把逻辑删除说成物理安全擦除。
数据清理与保留期限仍待用户选择；正式设计应说明是否以及多久会清理备份。

## 5. 自主记忆的写入和纠正

当前 Phase 7.1 仅有显式写入和经确认的候选；目标增加有长期授权的自动写入路径。
迁移应保留原有 Explicit / Inferred / UnverifiedSelection 的实际含义，
不能为了兼容自动写入而伪造旧字段中的逐项用户确认时间。

建议新增或扩展来源与授权证据：本次写入由哪个授权范围允许、依据哪些消息、
属于明确陈述还是推测、适用时间/项目、当前有效性、关联修正记录。
正式 schema 迁移尚未设计。

自然语言纠正建议流程：

1. 识别当前交流中被纠正的认识与可能受影响的来源。
2. 有明确指向且权限允许时修正；范围含糊或涉及批量删除时询问必要问题。
3. 保留新陈述与旧认识的关联，更新检索和失效标记。
4. 更新或失效派生摘要、人物认识及缓存，防止旧结论再次注入。
5. 反馈实际完成范围，不把一句道歉当作修正完成。

短期印象需要证据和时效，不自动生成永久人格标签。
删除记忆与删除聊天档案是不同操作；界面应让用户理解剩余数据，而不是偷偷保留或全部抹除。

## 6. 观察、行动、发送是独立授权维度

未来长期授权的候选字段：授权主体、来源范围、动作、目标/接收者、设备/项目、
有效期、预算、撤销状态和必要的再次确认条件。此处不冻结字段名或授权 DSL。

权限判断发生在可信 Kernel/设备执行边界，不能由模型输出“已获许可”代替。
内容可以影响选择做什么，不能修改权限本身。对外发送前要重新检查撤销与目标范围。

| 行为 | 允许依据 | 不能隐含获得 |
| --- | --- | --- |
| 观察 QQ 群 | 来源白名单 | 群内发言和管理权限 |
| 私聊用户 | 绑定身份与交流授权 | 联系其好友 |
| 写自主记忆 | 来源/动作长期授权 | 改写人格根规则或凭证 |
| 获取外部 Worker 历史 | 本机采集授权 | 接管进程、发送指令、审批 |
| 跟进一项工作 | 目标和工作范围 | 扩大沙箱、预算和任务 |
| 使用模板 | 对应资源权限 | 公开私人样例和全部聊天 |

现有逐次确认在新授权服务实现、测试和迁移前继续执行。
产品上允许有限自主不意味着开发代理现在可以运行付费测试、登录 QQ、采集真实聊天或部署。

## 7. 后台活动与发送生命周期

将“观察到事件”“决定做事”“完成活动”“想分享”和“已发送”分别记录。
建议的活动生命周期：待调度、执行中、完成、失败、结果不确定、取消/到期。
这些状态属于活动，不复用 Worker Turn 来假装生活事件都是编码任务。

通知候选建议携带来源事件、原因、有效期、紧急等级、目标、最近尝试和去重键。
调度读取课表、勿扰、近期发送频率与未回应状态，再决定发送、延后或丢弃。
课表更新后要重新评估排队消息，不能因早先已计划便忽略新的勿扰。

云端在外部发送前保存发送意图，收到可靠回执后记录结果。
发送请求超时但消息可能已送达时，不能盲目重发；如果平台不能查询确认，显示不确定，
采用不会无限重复打扰的恢复策略。数据库事务不能保证外部 QQ 消息 exactly-once。

重启后应检查待办时效，避免把一夜积压的闲聊集中补发。
“没有回复”不等于用户已读或讨厌某话题，不应据此产生确定的关系判断。

## 8. 设备执行与失联恢复

设备应显式配对、可撤销，能力报告包含平台、可用 Worker、可访问工作区和最后联系时间。
敏感凭证留在对应受控边界；不将设备的通用 shell 作为聊天模型的无限工具。
允许哪些轻量 PC 操作需要逐项能力设计，不把“本地交互”解释成全屏监控或任意操作。

云端意图、设备接受、Worker 提交、实际运行、终态证据与用户看到结果分别记录。
断线恢复重放的是记录与可安全查询，不是未经判断地重放变更命令。
同一逻辑命令有稳定身份；无法证明是否执行时保留 Unknown 并核对执行证据。

设备关闭时，云端可继续接收社交消息、阅读与聊天。不能自动把未完成本地工作迁移
到另一台机器，因为路径、权限、工具、运行现场和副作用可能不等价。
跨机器恢复或迁移属于将来的明确能力，不能以复制聊天记录假装完成。

## 9. 外部 Worker 档案与控制权

档案接入和运行控制是两种能力，可以来自不同接口。适配器应报告支持的范围：
历史读取、实时增量、部分内容、只读观察、恢复、发送、取消、审批、原生入口。
不要因为具备历史文件读取能力就标记为可管理 session。

外部会话保留 provider 身份在适配层，由 Lain 档案 ID 关联设备和项目。
历史导入不制造活跃 WorkSession，不把工具中不存在的终态补成 Completed。
接管需要用户明确指示以及后端能力支持；不能启动同名新 session 冒充原会话。

当前会话快照、有限规范化历史、未来可见 transcript 档案应分别说明完整性。
不承诺所有工具都开放同等记录，也不采集隐藏推理来补足“完整”二字。

## 10. 工程验证与开放决策

实现前先形成窄范围协议与存储提案，至少覆盖以下确定性测试：

- 两个入口同时更新相关认识时，来源和版本不被最后写入覆盖。
- 群文本注入、伪造昵称、账号镜像、自发消息和重复事件不越权、不循环。
- 采集撤销后停止处理，已排队发送在执行前复核授权。
- 已保存/已读/已整理/已验证状态不混淆。
- 修正与删除使旧派生认识失效，缓存或再次导入不会悄悄复活它。
- 队列积压、发送回执丢失、进程重启与云端断连不导致无限重复消息。
- 外部档案只读，不获得控制权；接管失败不制造替代会话。
- 资源上限阻止无界唤醒，重要工作状态不会因节流丢失。

真实 QQ、真实模型、真实设备和多日体验另列验收；假服务不能替代它们。
部署拓扑、协议、资源数值、存储保留与授权 UI 均待决定。
