## Upgrade procedure

1. Identify the exact source snapshot, native Linux binary hash and passing
   native checks. Preserve uncommitted-source provenance rather than inventing a
   commit. Confirm there is no active builder modifying that output.
2. Record current selector, binary hash, schema, service state and the current
   business-state boundary. Preserve all credentials and configuration. Rehearse
   migration and rollback with an isolated consistent copy first.
3. Produce and verify a fresh consistent pre-upgrade archive with its database
   hash, schema and release manifest. Check bounded retention and recovery
   readability. Do not overwrite the only usable backup. Save its exact identity
   in the private upgrade record.
4. Publish the new deployment-owned release with hashes. Stop the Kernel and
   confirm it has exited before any database replacement. Select the new release,
   start the service and let its transactional migrations run. Do not initialize
   a replacement database or copy a PC database over the cloud state.
5. Verify authenticated readiness, schema, retained identity, actual HTTPS/SSE,
   client startup and device behavior. A running process alone is insufficient.
   Record failures and apply the prepared rollback when necessary; do not retry
   uncertain Worker or permission effects to make a check pass.
6. Keep current and previous known-good binaries plus the matching pre-upgrade
   database backup. Remove only manifest-owned older outputs after acceptance.
   Never run global container/cache cleanup.

## Database rollback and recovery

An older binary rejects a newer schema. Restoring only `/srv/lain/current` cannot
complete rollback. Preserve failed-version state/evidence, stop the Kernel, verify
exit and restore the exact matching consistent pre-upgrade database. Restore
ownership/private permissions and handle only that stopped database's WAL/SHM
files; never delete active SQLite sidecars. Select the matching old binary,
restart, then verify readiness, schema and public authenticated access again.

Rollback returns to the backup's state. Any later work must be accounted for
explicitly; pending/unknown execution evidence cannot be manufactured or replayed.
Restoration does not authorize enabling channels, importing personal archives or
changing model configuration.
